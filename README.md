# ARG ERP — standalone HR

Working branch: `feature-dod`. The home page has three modules: **Human Resources**, **Organization**, and **Auth**. The React/MUI frontend keeps the existing green theme. Sign-in is required; there are no screen/action permission checks. Existing leave and payroll business flows remain. Loan, Vacancy and Organogram screens/routes have been removed.

## Local start

Requires .NET 9 runtime, a compatible .NET SDK, Node.js, Docker Desktop (running) and SQL Server LocalDB (`MSSQLLocalDB`). Run from this folder:

```powershell
npm --prefix frontend ci
dotnet build ARGERP.sln
./scripts/setup.ps1
./scripts/start.ps1
```

Open http://localhost:3000 and sign in as **admin**. The generated password is the `adminPassword` value in `.local/settings.json`. Keep that file: it also holds the local signing key. Use **Auth ? Users** to create/update users, link employees, set default branches, reset passwords and deactivate accounts. Use **Auth ? Change Password** for your own password. Deactivation/password changes revoke existing sessions across services. Existing EDXS passwords/accounts are not migrated.

`./scripts/stop.ps1` stops only the saved ARG launchers and their children. `-BackendOnly` leaves the frontend running. Build while the backend is stopped to avoid Windows executable locks.

## Separate database

All ARG services use **ARGERP_HR** on `(localdb)\MSSQLLocalDB`, with Windows integrated authentication. Setup checks the database name and adds missing tables/columns without resetting data. EDXS databases are never setup targets. Do not use `--recreate-empty` against a populated database.

`database/001-schema.generated.sql` is generated by the setup utility; `002-support.sql` holds standalone support data and `003-demo.sql` adds clearly labelled synthetic examples. Demo employees have no machine code, so real biometric punches cannot attach to them. Rerunning setup does not duplicate demo rows. SQL backups should include ARG tables, workflow records, local authentication, ZKT links and import receipts together.

## ZKT integration

See [the integration notes](docs/zkt-integration.md). Credentials are stored only in ignored `.local/zkt-source.json` and `appsettings.Local.json`. Setup preserves this configuration when regenerating service settings.

## Services

| Service | Local port |
| --- | --- |
| Frontend | 3000 |
| YARP gateway | 5181 |
| Human Resource | 5182 |
| Organization / local authentication | 5183 |
| HR approvals | Inside Human Resource (5182) |
| Aspire AppHost dashboard | 18880 |

AppHost starts dedicated `argerp-redis` and `argerp-rabbitmq` Docker containers, waits for them before starting dependent services, and injects their connection strings. Redis is used for workflow replay protection and the SignalR backplane. RabbitMQ is running and referenced by the service configuration; the standalone flows currently use SQL and HTTP and do not publish queue messages. RabbitMQ data uses the `argerp-rabbitmq-data` volume.

SQL remains the existing standalone LocalDB database, exposed to the AppHost as the external `OrganizationDB` and `UserManagementDB` connection resources. Both keys currently point to `ARGERP_HR`. AppHost does not recreate or rename the SQL database. The requested remote SQL change was cancelled; active settings remain local.

The AppHost dashboard is configured for anonymous local development access. These HTTP settings are for the local workstation.

## Validation commands

```powershell
dotnet build ARGERP.sln
dotnet test tests/HumanResource.Service.Tests
npm --prefix frontend run build
node tests/screen-render.cjs
dotnet run --project tools/DatabaseSetup -- --test-zkt
# With the local app running:
node tests/api-smoke.mjs
node tests/crud-smoke.mjs
node tests/auth-smoke.mjs
node tests/hr-flows.mjs
```

The ZKT integration test creates a temporary, uniquely named local fixture database, checks history/idempotency/source isolation and removes its fixtures. It does not contact the real ZKT server. Screen rendering is a server-render check; interactive browser/visual verification is a separate check.

The login presentation, logo, home portal and menu cards reuse the original project's Al Rahim Group assets and JSX. The navigation shell keeps its sidebar/header dimensions and styling while exposing the three standalone modules. Login branding is always Al Rahim Group, including localhost.

For Visual Studio, select the `AppHost` launch profile and press F5. The checked-in profile supplies the dashboard and telemetry environment variables. Use one backend launcher at a time: before switching from the script to Visual Studio, run `powershell -File scripts/stop.ps1 -BackendOnly`, stop any old debugging session, then rebuild. The stop script detaches only ARG's own brokers from the recorded ARG launch network and removes that network once empty; broker data volumes remain intact.


Only HR, Organization and Auth business modules are included. Auth is hosted in Organization.Service. Approval execution and payroll posting run inside HumanResource.Service; there is no standalone Workflow or Finance project. HR supporting lookups, settings, teaching references and reporting read local HR APIs. Gateway exposes only HR, Organization/Auth and local users.

Run `powershell -File scripts/build.ps1` for a guarded build, or add `-ArtifactsPath .local/build` to verify without replacing running outputs. Setup/start/build run `scripts/assert-scope.ps1` to reject excluded services and module API references. Repository instructions are recorded in AGENTS.md.

HR report previews and exports are generated locally from scoped HR API data (PDF and XLSX); no external report server is required. Original report templates and the previous extra export formats are not included.
